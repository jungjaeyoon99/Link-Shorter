# JJY Links — 확장 버전

기존 정적 GitHub Pages 프로젝트를 기반으로 접속 기록, IP별 브라우저 측 접속 횟수 제한, 객관식 설문, 설문 통계, 만료 시각 빠른 설정, 관리자 로그 화면을 추가한 버전입니다.

## 파일

- `index.html` — 화면 구조
- `styles.css` — 화면 스타일
- `app.js` — Firebase Authentication / Realtime Database 연동
- `firebase-rules.json` — Realtime Database 보안 규칙

## 적용 순서

1. GitHub Pages 저장소의 기존 파일을 백업합니다.
2. 위 네 파일을 저장소의 기존 파일과 교체합니다. `app.js`는 `index.html`과 같은 폴더에 둡니다.
3. Firebase Console → Realtime Database → Rules에서 `firebase-rules.json` 내용을 게시합니다.
4. Firebase Authentication에서 이메일/비밀번호 로그인이 활성화되어 있는지, GitHub Pages 도메인이 승인된 도메인인지 확인합니다.
5. `roles/{관리자 UID}` 값이 문자열 `admin`인지 확인합니다.
6. 관리자 계정으로 로그인해 접속 로그 패널이 표시되는지 확인하고, 비관리자 계정에서는 패널과 비공개 로그 읽기가 차단되는지 확인합니다.

Firebase 웹 설정은 브라우저에 공개되는 값입니다. API 키를 비밀로 취급하기보다 Realtime Database Rules와 Authentication 권한을 정확히 설정해야 합니다.

## 추가 기능 사용

### IP별 접속 횟수 제한

관리자 계정에서만 링크별 설정 편집 UI가 표시됩니다. 설정은 `rateLimitSettings/{customPath}`에 저장되며, 기존 링크의 `rateLimitEnabled`, `rateLimitMax`, `rateLimitMessage` 값은 새 설정이 없는 동안 읽기 호환 fallback으로 사용합니다. 신규 링크의 제한 설정은 링크 레코드와 분리하여 저장합니다.

**중요한 배포 차단 사항:** 이 프로젝트는 GitHub Pages에서 실행되는 정적 브라우저 앱입니다. 브라우저의 `runTransaction()`만으로 IP별 카운터를 안전하게 갱신하면서 동시에 카운터 읽기를 관리자에게만 허용하는 것은 불가능합니다. RTDB transaction은 기존 값을 읽어야 하기 때문입니다. 현재 Rules는 `rateLimits/{customPath}`의 읽기/쓰기를 관리자에게만 허용하므로, 방문자 요청의 카운터 증가는 신뢰할 수 있는 서버(예: Cloud Functions + Admin SDK)에서 처리해야 합니다. 서버 함수가 연결되기 전에는 제한이 활성화된 링크에서 카운터 확인 오류가 나면 우회 허용하지 않고 차단 메시지를 표시합니다. 즉, 이 ZIP만으로는 활성 제한이 정상 작동한다고 간주하면 안 됩니다. 서버 함수에서 실제 요청 IP를 얻고 transaction을 수행한 뒤 redirect 허용 여부를 반환하도록 구현·배포해야 합니다.

### 접속 로그

유효한 단축 링크에 접속하면 원본 URL로 이동하거나 설문을 표시하기 전에 접속 로그를 한 번 저장합니다. 설문을 취소하거나 제출하지 않아도 최초 접속 로그는 별도로 유지됩니다. 설문 응답에는 최초 접속 때 발급한 `accessLogId`만 저장하며, 제출 과정에서 접속 로그를 다시 생성하지 않습니다.

수집 항목은 IP 주소, 접속 시각(timestamp), 브라우저 및 운영체제 정보(User-Agent)입니다. IP 조회에는 `https://api.ipify.org`를 사용합니다. 해당 서비스 장애·시간 초과 시 IP 값은 `unavailable`로 기록을 시도하며, IP 기반 접속 횟수 제한은 적용할 수 없습니다. 로그 저장 실패와 원본 URL 이동은 별도로 처리합니다. 브라우저 종료, 네트워크 중단, Firebase 장애 등의 경우 저장 성공을 보장할 수 없습니다.

관리자(`roles/{uid}` = `admin`)만 `privateAccessLogs`를 읽을 수 있습니다. 일반 사용자는 다른 사용자의 접속 로그를 읽을 수 없습니다. 비로그인 방문자도 로그를 생성할 수 있어야 하므로 로그의 신규 쓰기는 공개 링크 경로에 허용되지만, 기존 로그의 수정·삭제는 허용하지 않습니다.

실제 운영 전 개인정보 처리 목적, 운영 주체, 수집 항목, 외부 IP 조회 서비스 이용, 구체적인 보관 기간, 파기 방법 및 문의처를 확정해 방문자에게 안내해야 합니다. 현재 프로젝트에는 자동 보관 기간 만료·삭제 기능이 없으므로 관리자가 보관 기간에 따라 Firebase에서 직접 삭제해야 합니다.

### 설문

- `숫자 입력`: 숫자 응답
- `문자 입력`: 기존 동작대로 관리자만 설정 가능
- `객관식 · 하나 선택`: 라디오 버튼
- `객관식 · 여러 개 선택`: 체크박스
- 객관식 선택지는 한 줄에 하나씩 입력하며, 최소 2개·최대 30개입니다.
- 관리자/링크 생성자는 응답표와 객관식 선택 비율을 확인할 수 있습니다. 복수 선택 문항의 비율은 응답자 중 해당 항목을 선택한 비율이므로 합계가 100%를 넘을 수 있습니다.

### 만료 시각

`+1시간`, `+1일`, `오늘 자정` 버튼은 현재 브라우저의 현지 시간을 기준으로 만료 입력란을 채웁니다.

## 데이터 경로

- `privateAccessLogs/{customPath}/{logId}` — IP, User-Agent, 접속 시각, 선택적으로 설문 응답 ID
- `surveyResponses/{customPath}/{responseId}` — 설문 답변, 동의 여부, 제출 시각, 접속 로그 ID
- `rateLimitSettings/{customPath}` — 관리자 전용 링크별 설정(enabled, max, message, updatedAt, updatedBy)
- `rateLimits/{customPath}/{ipHash}` — 서버 측에서 관리해야 하는 IP 해시별 누적 접속 횟수
- `surveyConfigs/{customPath}` — 설문 질문과 선택지

## 개인정보 및 보관

IP 주소와 User-Agent는 개인정보 또는 개인정보와 결합 가능한 정보가 될 수 있습니다. 실제 공개 전 운영 주체, 수집 목적, 외부 IP 조회 서비스 사용, 보관 기간, 삭제 방법, 문의 방법을 구체적으로 정하고 사이트에 명시해야 합니다. 이 프로젝트는 자동 보관기간 만료·삭제 기능을 제공하지 않으므로 관리자가 정한 보관 기간에 따라 Firebase에서 직접 삭제해야 합니다. 필요 이상으로 오래 보관하지 마세요.

## 기존 데이터 주의

기존 규칙에 있던 `links/{customPath}/logs` 경로는 더 이상 사용하지 않습니다. 기존 로그 데이터가 있다면 새 `privateAccessLogs` 경로로 자동 이동되지 않습니다. 또한 새 규칙을 게시하면 로그인 로그는 관리자만 읽을 수 있도록 변경됩니다.

## 한계와 운영 주의

- 브라우저에서 저장한 IP 및 User-Agent는 방문자가 위조할 수 있습니다.
- IP 주소가 같아도 여러 사람이 같은 네트워크를 공유할 수 있고, 한 사람도 네트워크 변경으로 다른 IP를 사용할 수 있습니다.
- 관리자 로그 화면은 링크별 최신 100건을 먼저 가져오고, `이전 로그 더 불러오기`로 100건씩 추가 조회합니다. 링크별 조회 실패는 다른 링크 결과를 중단하지 않습니다. 필터의 건수는 현재 로드된 로그 기준이며 전체 보관 건수의 서버 집계값은 아닙니다.
- 로그는 timestamp와 로그 ID를 함께 사용해 정렬/중복 제거합니다. 대규모 전체 건수 집계나 복합 필터의 서버 측 페이지네이션은 별도 서버 API가 필요합니다.
- IP 제한 카운터의 신뢰성 및 실제 클라이언트 IP 판별은 Cloud Functions 등 서버 측 구현이 필요합니다.
